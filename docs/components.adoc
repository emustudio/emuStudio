== Components

Runner:: The picocli command that boots the platform. It lists configurations,
resolves the selected virtual computer (by name/index/file or via a GUI
chooser), builds the `ContextPool`, loads the `VirtualComputer` and either shows
the main window or hands off to automation.

AutomationCommand / Automation:: The headless path. `AutomationCommand` is the
`automation` subcommand; `Automation` performs the unattended sequence — compile
the input file, reset the CPU (optionally at a start address), execute, wait for
completion and log the resulting CPU run state. It uses the machine-owned
`EmulationController`, as do GUI commands and debug scripts.

ConfigFiles / Settings:: Reads and writes the TOML configuration and settings
model — `ComputerConfig` (a machine and its `PluginConfig` entries plus
`connections`) and `AppSettings` (global options). Backed by the night-config
TOML library.

VirtualComputer:: The heart of Level 3. It groups a machine's plugins by type
(`COMPILER`, `MEMORY`, `CPU`, `DEVICE`), constructs them, initializes them in a
fixed order and owns their execution controller and disposal. CPU-less machines
use that controller for memory and compiler mutations too. It also implements `PluginConnections#isConnected`,
the authority the context pool consults before letting two plugins share a
context.

PluginLoader:: Loads plugin JARs into a dedicated `URLClassLoader` (including
each JAR's declared `Class-Path` dependencies), scans the classes and returns
the single loadable main class for each configured JAR — the one that is
annotated `@PluginRoot` and implements the `Plugin` contract. The
`VirtualComputer` owns that class loader and closes it during shutdown.

ContextPool:: The mediator through which plugins communicate. Plugins *register*
the contexts they provide and *request* the contexts they need; the pool matches
them by exact Java interface identity and only shares a context between plugins that are
connected in the current configuration (emuStudio itself is always allowed).
Subinterfaces and separately declared interfaces must be registered explicitly, even when
their methods are identical; a compatible method shape does not establish Java type identity.

ApplicationApi:: The facade handed to every plugin at construction time. It
exposes the `ContextPool`, the `Dialogs` and `GUI` services
and the current program location — the plugin's whole view of the host.

EmulationController:: Owns lifecycle state and explicit command completion for one
machine. Its command scheduler stays available while a separate machine worker
runs synchronous CPU execution, stepping, resets, compilation, and paused edits.
CPU plugins and `AbstractCPU` create no execution pools. The scheduler also samples
CPU frequency, avoiding a separate sampling pool.
+
Pause, stop, reset, replacement timed runs, and close cancel timed stepping. Each
next tick follows completion of the previous instruction plus the requested delay;
generation checks prevent a cancelled sequence from resuming. Stop requests are
cooperative, with no force kill or deadline. Pending reset or close waits for actual
execution exit; the host retains resources and rejects further mutations until then.
GUI callers observe completion asynchronously, while automation and scripts may wait
off Swing. State listeners observe transitions rather than acknowledging commands.

GUI (EmuStudioGui, Schema editor, Source editor, Debugger, Dialogs):: The Swing
front end. The main window hosts the three work areas and provides the emuLib
`GUI` and `Dialogs` services that plugins may use to render settings dialogs and
messages.

== How a virtual computer comes to life

. `Runner` selects a `ComputerConfig` and creates a `ContextPool`.
. `VirtualComputer.create()` asks `PluginLoader` to load the plugin JARs and
  find each `@PluginRoot` main class.
. Each plugin is constructed by reflection with `(pluginId, ApplicationApi,
  PluginSettings)`.
. `initialize()` is called per plugin in the order *compiler → memory → CPU →
  devices*; during initialization plugins publish and look up contexts in the
  `ContextPool`.
. The GUI, automation, and debug scripts drive emulation through the same
  machine-owned `EmulationController`, with the context pool
  enforcing the configured connections throughout.
